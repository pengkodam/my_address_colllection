| --- | --- |

| `make_review_sheet.py` | Build a blind precision-review sheet from validator results. |

only if you have a licensed registry export. The scraper is the last resort.

## Polite Yellow Pages scraper

A single-threaded Python scraper for `yellowpages.my` that is built to be slow,
cache everything, resume after interruptions, and **stop** instead of hammering
the site when it pushes back.

It uses the same public JSON endpoints the Angular site uses
(`api.yellowpages.my/post/search` and `profile/slug/...`), plus the SSR HTML for
the category tree.

## What I found while probing the site

These facts shaped the defaults in this tool:

| Check | Result |
| --- | --- |
| `robots.txt` | `404` on both `www` and `api` hosts (no published rules) |
| Front door | Cloudflare; headless browsers get a "Just a moment..." challenge |
| Search API | `POST /post/search` returns `500` for real listing queries right now |
| `GET /home`, `GET /states`, SSR category page | work |
| Unknown/bogus category queries | sometimes return `200` with 0 results |

The `500` is generated by the origin (`X-Powered-By: PHP/7.4.13`), not by this
script, and it happened even for queries that had worked minutes earlier. That
is why the tool caps failures and refuses to retry in a loop. If search is down
when you run it, wait (hours, not seconds) and try again — do not lower the
delays to "get it over with".

## Install

```powershell
py -3 -m pip install -r requirements.txt
```

## Use

Always pass a real contact address; it is embedded in the User-Agent so the
site owner can reach you instead of silently blocking you.

```powershell
# See all valid category slugs (one page request)
py -3 yp_scraper.py categories --email you@example.com

# Check the endpoints before a run
py -3 yp_scraper.py probe --email you@example.com

# Scrape restaurants in Kuala Lumpur, one page
py -3 yp_scraper.py search `
  --email you@example.com `
  --type services --parent food-dining --sub restaurants `
  --where "Kuala Lumpur" `
  --pages 3 `
  --out data/kl_restaurants
```

Global flags may go before or after the subcommand.

Useful options:

| Flag | Default | Why |
| --- | --- | --- |
| `--delay` | `6` s | Base gap between every request |
| `--jitter` | `4` s | Random extra gap, so traffic is not metronomic |
| `--retries` | `3` | Attempts on 5xx/429 only, with exponential backoff |
| `--max-failures` | `5` | Abort after this many consecutive failures |
| `--max-requests` | `300` | Hard cap per run |
| `--pages` | `1` | Pages per run; safe to resume later |
| `--max-records` | `200` | Stop after this many new records |
| `--details` | off | Also fetch each profile page (doubles requests) |
| `--no-cache` | off | Ignore the on-disk response cache |
| `--restart` | off | Ignore saved progress |
| `--form` | off | Send form-encoded bodies instead of JSON |

## Politeness features

1. **One request at a time**, with 6 s + up to 4 s jitter by default (~8 s
   average). A 3-page run is roughly 25 seconds of requests, plus backoff.
2. **Disk cache** (`cache/`, 7-day TTL). Re-running never re-fetches a page it
   already has.
3. **Resume**: progress is saved in `<out>.state.json`; records are appended to
   `<out>.jsonl` and deduplicated by slug.
4. **Robots check** before the first request to each host. A 404 is treated as
   "no published rules", not as permission to ignore common sense.
5. **Cloudflare is never bypassed.** On a challenge the tool raises `BlockedError`
   and exits with code `2`.
6. **Hard stops**: 403/401, a challenge, the request cap, or repeated 5xx
   failures all end the run (exit codes `2` and `3`) instead of retrying forever.
7. **`Retry-After` is obeyed** when the server sends it.

No approach can guarantee you will not be blocked. The only guaranteed-safe
option for bulk use is to ask Yellow Pages Malaysia for an API or data licence.

## Output

For `--out data/kl_restaurants`:

* `data/kl_restaurants.jsonl` — one full API record per line
* `data/kl_restaurants.csv` — flattened columns for spreadsheets
* `data/kl_restaurants.state.json` — next page per query, so you can resume

CSV columns: `id, ref_id, slug, title, type, plan, rating, rating_count,
summary, address, locations, phones, categories, parent_categories, lat, lon,
url, scraped_at`.

With `--details`, the full profile response is stored under `detail` in the
JSONL file (not flattened into CSV).

## When it fails

* **HTTP 500 from `/post/search`** — the origin search service is unhealthy.
  The tool stops after the failure cap. Wait and retry later. Do not run it in a
  `while` loop.
* **Cloudflare / "Just a moment"** — stop. Use a normal browser manually if you
  need a page, or wait. This tool intentionally does not solve challenges.
* **HTTP 429** — you are going too fast. Raise `--delay`, lower `--pages`.
* **`--type services` returns 500 immediately** — pass `--parent` (and usually
  `--sub`). The API errors when the parent category is missing.
* **HTTP 502** on profiles — transient origin problem; retry much later.

## Legal / ethical note

Scraping publicly accessible pages is not automatically permitted. Check the
site's terms of use, keep the request volume negligible, do not republish the
directory in bulk, and prefer contacting them for licensed data. This script is
a rate-limited research tool, not a bulk-extraction pipeline.

# No-scraping alternative: Overture Maps extractor

`overture_my.py` builds a Malaysian business-place dataset from **Overture Maps**
instead of scraping anyone. It reads Overture's public Parquet release with
DuckDB — no requests to `yellowpages.my`, no rate limits, no Cloudflare.

The places theme is licensed **CDLA-Permissive-2.0 / Apache-2.0** depending on
the source, so commercial use is allowed. Each row carries `source_datasets` and
`source_licenses`; keep them.

## Install

```powershell
py -3 -m pip install -r requirements.txt
```

DuckDB downloads the `httpfs` and `spatial` extensions on first run.

## Workflow

`pull` scans the **global** dataset once and writes a small local Parquet file.
`export` then slices that file instantly, with no network access.

```powershell
# 1. One expensive pass: Malaysia, confidence >= 0.6
py -3 overture_my.py pull --out data/my_places_raw.parquet --min-confidence 0.6

# 2. Fast local slices (no network)
py -3 overture_my.py export `
  --input data/my_places_raw.parquet `
  --out data/kl_restaurants `
  --category restaurant --state "Kuala Lumpur" `
  --require-contact --dedupe --formats parquet,csv,jsonl

# 3. Coverage report
py -3 overture_my.py stats --input data/my_places_raw.parquet --top 30

# City-sized output (still scans globally, but limits what is written)
py -3 overture_my.py pull --out data/kl_raw.parquet `
  --bbox "101.5,3.0,101.8,3.3" --min-confidence 0.6

# Smoke test: 5 rows from anywhere, no country filter
py -3 overture_my.py pull --out data/test.parquet --all-countries --limit 5
```

## What you get

`gers_id, name, brand, brand_wikidata, basic_category, category, category_path, address,
locality, region, postcode, country, phones, phone, emails, email, websites,
website, socials, lat, lon, confidence, operating_status, source_datasets,
source_licenses, source_count`

Plus `<out>.meta.json` recording the release, filters, row count and licence.

`export` adds (or preserves) one extra column, `state`, derived from region,
postcode and locality. `pull` does not, because the derivation needs the whole
file to learn the locality lookup (see below).

## Reality check on performance

* The places theme has no country partition, so `pull --country MY` still reads
  a large part of a global dataset. Expect **tens of GB of scanning** and a long
  first run. Use `--memory-limit 8GB` and `--temp-dir D:\duckdb_tmp` if needed.
* Run it on an **AWS EC2 instance in `us-west-2`** (same region as the S3 bucket)
  or an Azure VM in the matching region to avoid egress fees. A home connection
  will work, but the download is the bottleneck.
* Subsequent `export` runs read only the local Parquet file and take seconds.
* Releases are monthly. Bump `--release` (for example `2026-11-18.0`) and check
  `docs.overturemaps.org/release-calendar/`. The default here is `2026-10-21.0`,
  the release this script was tested against.
* `--bbox` limits output and may help Parquet row-group pruning, but do not
  expect it to avoid most of the scan.
* `export` accepts either a pulled file or a raw Overture Parquet/glob, so you
  can also use the Overture CLI to download a bbox extract first.

## Filters that matter for lead quality

| Flag | Effect |
| --- | --- |
| `--min-confidence 0.7` | Drop low-confidence junk; Overture itself warns about junk |
| `--require-contact` | Keep rows with at least one phone, email or website |
| `--open-only` | Keep only `operating_status = 'open'` |
| `--dedupe` | One row per normalised name + coordinates, highest confidence |
| `--category restaurant` | Matches category, full hierarchy, or basic category |
| `--state "Kuala Lumpur"` | Derived state; accepts names, ISO codes, `penang`, `KL` |
| `--region "Kuala Lumpur"` | Raw Overture `region` — sparse and unreliable; prefer `--state` |

Overture is a POI dataset, not a company registry. It does not cover dormant
companies, sole proprietors without a physical POI, or B2B firms with no public
location. For those, combine it with SSM e-Search/MyDATA, ePerolehan, JAKIM or
the relevant regulator list as described in the discussion.

## Address coverage and derived state

`stats` reports how much contact and address data a pull actually contains:

```powershell
py -3 overture_my.py stats --input data/my_places_raw.parquet --top 30
```

On the `2026-10-21.0` Malaysia pull used to test this (533,583 rows, confidence
>= 0.6, closed excluded):

| Field | Rows | Share |
| --- | --- | --- |
| `address` (freeform street) | 428,104 | 80% |
| `postcode` | 422,963 | 79% |
| `locality` | 526,494 | 99% |
| `region` (raw Overture) | 25,908 | **5%** |
| address + postcode + locality | 398,569 | 75% |

The raw `region` field is not usable for filtering. It is populated for only 5%
of rows and mixes English names (`Selangor`, `Penang`, `WP Kuala Lumpur`) with
ISO 3166-2:MY codes (`01`, `10`, `14`). Name-based values conflict with the
postcode range 10–20% of the time; the ISO-coded values agree 98%+. Postcode is
therefore the stronger signal.

`export` derives a `state` column instead:

1. normalise `region` (names, ISO codes, aliases such as `Penang`, `KL`,
   `Johor Darul Ta'zim`);
2. map the postcode's first two digits to a state (`01`–`02` Perlis, `05`–`09`
   Kedah, `10`–`14` Pulau Pinang, …, `93`–`98` Sarawak, with the Pahang
   enclaves `39`, `49`, `69` and Selangor's `63`/`64`/`68`);
3. learn a locality → state lookup from rows where the first two signals agree.

Two agreeing signals win; otherwise postcode is preferred, then locality, then
region. On the test pull this covers 99% of rows. Treat it as a derived aid, not
an authority: ambiguous localities (for example `Batu`) and bad upstream rows
still produce occasional errors.

```powershell
py -3 overture_my.py export `
  --input data/my_places_raw.parquet `
  --out data/penang_restaurants `
  --category restaurant --state penang --dedupe
```

## Release diffing

Monthly releases mean businesses open, close, move and change phone numbers.
Compare two pulls to get a change set:

```powershell
py -3 overture_my.py diff `
  --old data/my_places_2026_09.parquet `
  --new data/my_places_2026_10.parquet `
  --out data/changes
```

Outputs `changes_added.*`, `changes_removed.*` and `changes_changed.*` (the
changed file keeps `old_name`, `old_phone`, and so on for comparison). Use this
to re-verify only the delta instead of re-scraping everything.

# Organizations without a registry: `derive_orgs.py`

You do not need SSM to build a usable company layer. `derive_orgs.py` groups
outlets that share identity signals, producing organizations bottom-up:

| Signal | Weight | Why |
| --- | --- | --- |
| Same Overture `brand.wikidata` QID | 0.85 | Strongest possible brand key |
| Same non-generic website domain | 0.70 | One brand, many branches |
| Same full phone number | 0.50 | Shared switchboard or owner |
| Same brand name | 0.45 | Overture's own brand field |
| Same social handle (FB/IG/TikTok/LinkedIn) | 0.40 | Shared digital identity |
| Same 7-digit phone suffix | 0.20 | Weaker phone signal |
| Name similarity (Jaro-Winkler) | up to 0.35 | Handles branch names |
| Postcode / address / distance | up to 0.20 | Local corroboration |

Conflicting domains, phones, states or Wikibase QIDs subtract points. Edges at
or above `--threshold` (default 0.72) are merged with union-find; edges between
`--review` (0.55) and the threshold are kept for human review.

## Workflow

```powershell
# 1. Load outlets (same loader as before)
py -3 resolve_entities.py init --db data/yp.duckdb --force
py -3 resolve_entities.py load-outlets `
  --db data/yp.duckdb --input data/my_places_raw.parquet

# 2. Cluster into organizations
py -3 derive_orgs.py derive --db data/yp.duckdb

# 3. Inspect
py -3 derive_orgs.py report --db data/yp.duckdb

# 4. Export
py -3 derive_orgs.py export --db data/yp.duckdb --out data/orgs

# 5. Enrich chain brands from Wikidata (free, cached, 1 req/sec)
py -3 derive_orgs.py enrich-wikidata `
  --db data/yp.duckdb --limit 25 --email you@example.com
```

## What you get

| Table | Contents |
| --- | --- |
| `organizations` | `org_id`, display name, brand, QID, domain, phone, category, outlet count, centroid, key type, evidence |
| `org_members` | outlet ↔ organization, canonical/branch role, join score |
| `org_edges` | every scored pair, auto/review/reject, signal booleans, JW, distance |

For network analysis, export the membership graph:

```powershell
py -3 derive_orgs.py graph --db data/yp.duckdb --out data/orgs.graphml
```

That gives organization and outlet nodes plus membership edges, ready for
Gephi or Cytoscape. The `org_hierarchy` view joins enriched brands to their
Wikidata parent organization when both are present.

Organization IDs are meaningful and stable:

* `wd:Q37158` — brand with a Wikidata QID
* `web:starbucks.com.my` — brand identified by domain
* `tel:60312345678` — shared phone
* `org:<hash>` — name-based fallback

`enrich-wikidata` adds the English label, description, official website, parent
organization, country and stock exchange for each QID. It caches responses in
`cache/wikidata/`, so repeat runs are free.

## Attach any public list as evidence

This is the creative part: you do not need one authoritative registry. Any
public list that names businesses can become an attestation source.

```powershell
py -3 derive_orgs.py load-evidence `
  --db data/yp.duckdb `
  --source jakim `
  --input jakim_halal_directory.csv

py -3 derive_orgs.py match-evidence --db data/yp.duckdb
```

The importer auto-detects name, registration no., address, postcode, state,
phone, website and category columns, and accepts an explicit
`--column-map-file` when the headers are unusual.

Matching uses domain, phone, name, postcode and address, with the same
auto/review thresholds. Results land in `org_evidence`; every match stores its
evidence JSON. Export includes `org_evidence.csv`.

Good free/attestation sources to attach:

| Source | What it attests |
| --- | --- |
| JAKIM / MyeHalal | Halal-certified manufacturers and premises |
| ePerolehan | Registered government suppliers + award notices |
| MyIPO | Trademark applicants (brand ownership) |
| NPRA / data.gov.my | Licensed pharmaceutical, cosmetic, importer/wholesaler entities |
| CIDB | Registered construction contractors |
| FMM, ACCCIM, DPMM, MICCI, AMCHAM, EuroCham | Manufacturer/chamber membership |
| MATRADE | Malaysian exporters |
| Bursa Malaysia + annual reports | Listed companies and subsidiaries |
| GLEIF | Legal Entity Identifiers for larger corporates |
| Trade-show exhibitor lists (MIHAS, MIFF, ARCHIDEX, OGA, FHM) | Active, categorised companies |
| Wikidata | Brand identity, parent org, official site (built in) |
| Common Crawl + schema.org | Websites, emails, phones without touching the sites |

Each source is independent. A company that appears in three lists is more
trustworthy than one that appears in none, even if no single list is complete.

Evidence matches have their own review page:

```powershell
py -3 derive_orgs.py review-evidence-html `
  --db data/yp.duckdb --out data/evidence_review.html
```

Confirm/reject decisions download as `evidence_decisions.csv` with
`action` = `confirm_evidence` or `reject_evidence`. They are re-applied after
every `match-evidence` run.

## Correcting the graph with human decisions

The graph is heuristic, so the review queue must be actionable. Decisions are
stored in `review_decisions` and re-applied automatically after every `derive`,
so a re-cluster never silently undoes your corrections.

```csv
action,org_a,org_b,outlet_id,target_org,note
merge,wd:Q37158,web:starbucks.com.my,,,same brand
assign,,,ov:abc123,web:newbrand,split a branch
exclude,,,,ov:closed99,permanently closed
```

```powershell
py -3 derive_orgs.py load-review --db data/yp.duckdb --input decisions.csv
py -3 derive_orgs.py apply-review --db data/yp.duckdb
```

Prefer a visual pass? Generate a self-contained review page:

```powershell
py -3 derive_orgs.py review-html `
  --db data/yp.duckdb --out data/review.html --limit 200
```

Open `data/review.html`, click **Same organization / Keep separate / Exclude B**,
then **Download decisions.csv** and feed it to `load-review`. The page is plain
HTML/JS, works offline, and sends nothing anywhere.

Actions:

* `merge` — move every member of `org_b` into `org_a`, delete `org_b`.
* `assign` — move one outlet into `target_org`; a new organization is created if
  the target does not exist.
* `exclude` — remove an outlet from the graph (closed, duplicate, private).

Re-running `derive` re-applies these decisions and restores Wikidata/web
enrichment by `org_id`, so your corrections are not lost.

## Enriching from the business's own website

`enrich-web` fetches one homepage per organization, respects `robots.txt`,
waits 1.5 s between domains, caps the page at 2 MB and caches the HTML under
`cache/web/`.

```powershell
py -3 derive_orgs.py enrich-web `
  --db data/yp.duckdb --limit 25 --email you@example.com --follow-contact
```

It reads `schema.org` JSON-LD (`LocalBusiness`, `Organization`, `Store`, …) and
falls back to Open Graph/meta tags and `mailto:`/`tel:` links. With
`--follow-contact`, it fetches **one** contact/about page only when the homepage
yields no email or phone. Results land in `web_legal_name`, `web_email`,
`web_phone`, `web_address`, `web_description`, `web_same_as`,
`web_contact_url`, `web_status` and `web_fetched_at`.

It is deliberately shallow: one page, no link-following, no form submission,
and a hard `--limit`. Robots-disallowed and failed sites are recorded and
skipped on the next run unless you pass `--retry-errors`.

Enrichment survives re-clustering: `derive` snapshots and restores the
Wikidata/web fields by `org_id`.

## Why this is useful without SSM

* It works on the data you already have: outlets, domains, phones, socials.
* It finds **chains and multi-branch brands** that a flat POI list hides.
* It gives you a `key_type`, so you know whether an organization is anchored on
  a QID, a domain, a phone, or just a name.
* It does not pretend a name match is a legal entity. `org_edges` keeps the
  evidence, and review edges are explicit.
* Wikidata gives you free enrichment for recognizable brands without scraping
  anyone's website.

The obvious limits: a singleton independent shop stays a singleton; shared
phones (malls, co-working spaces) can over-merge; and a domain can host multiple
brands. The review edge table is where you correct those cases.

# Entity resolution: linking outlets to legal entities

> Use this only if you have a licensed SSM/registry export. If you do not,
> `derive_orgs.py` above is the recommended path.

`resolve_entities.py` turns the Overture extract plus an SSM-style export into a
linkable dataset. It never guesses silently: every link carries a score, the
component scores, and the evidence used.

## Schema

| Table | Purpose |
| --- | --- |
| `entities` | Legal entities: SSM no., name, status, MSIC, registered address, phone, website |
| `outlets` | Physical places: Overture GERS id, category, address, contact, coordinates |
| `links` | Candidate pairs with rank, score, decision, component scores, `evidence` JSON |

Views: `best_links` (top candidate per outlet), `matched_auto`, `review_queue`.

## One-shot build (recommended)

```powershell
py -3 resolve_entities.py build `
  --db data/yp.duckdb `
  --entities ssm_export.csv `
  --outlets data/my_places_raw.parquet `
  --out data/resolved `
  --dedupe-outlets --canonical-only
```

`build` starts from a **fresh** database, loads both sides, de-duplicates outlets,
resolves, prints the report and exports. For incremental work, use the manual
steps below.

## Workflow

```powershell
# 1. Create the database
py -3 resolve_entities.py init --db data/yp.duckdb --force

# 2. Load the Overture extract from overture_my.py
py -3 resolve_entities.py load-outlets `
  --db data/yp.duckdb --input data/my_places_raw.parquet

# 3. Collapse duplicate outlets (optional but recommended)
py -3 resolve_entities.py dedupe-outlets --db data/yp.duckdb

# 4. Load your SSM export (CSV, Parquet or JSONL)
py -3 resolve_entities.py load-entities `
  --db data/yp.duckdb --input ssm_export.csv

# 5. Link (only canonical outlets if you deduped)
py -3 resolve_entities.py resolve --db data/yp.duckdb --canonical-only

# 6. Inspect
py -3 resolve_entities.py report --db data/yp.duckdb --canonical-only
py -3 resolve_entities.py sql --db data/yp.duckdb `
  --query "SELECT * FROM review_queue ORDER BY score DESC LIMIT 20"

# 7. Export
py -3 resolve_entities.py export `
  --db data/yp.duckdb --out data/resolved --formats parquet,csv --canonical-only
```

Outputs: `data/resolved_matched.*`, `resolved_review.*`, `resolved_rejected.*`,
`resolved_unmatched.*`, plus `resolved.meta.json`. The four sets are mutually
exclusive: auto-linked, needs review, best candidate rejected, no candidate.

## De-duplicating outlets

Overture is known to contain duplicates, especially for chains and recently
moved businesses. `dedupe-outlets` blocks on phone suffix, domain, name+postcode
and name+address prefix, scores the pairs, and clusters the auto-merges with
union-find.

It writes `outlet_groups` and sets `outlets.group_id` / `outlets.is_canonical`.
The canonical outlet is chosen by Overture confidence, then contact completeness,
then shortest id. `resolve --canonical-only` then avoids counting the same shop
twice.

```powershell
py -3 resolve_entities.py dedupe-outlets --db data/yp.duckdb -v
py -3 resolve_entities.py sql --db data/yp.duckdb `
  --query "SELECT * FROM outlet_groups WHERE group_id IN (SELECT group_id FROM outlet_groups GROUP BY 1 HAVING count(*) > 1)"
```

## Column detection

Headers are auto-detected from English and Malay aliases
(`Company Name`/`Nama Syarikat`, `Registration No`/`No Pendaftaran`,
`Telephone`/`No Telefon`, `Poskod`, `Negeri`, and so on).

For unusual headers, use a JSON map. A file avoids PowerShell quoting problems:

```json
{
  "name": "Company Name",
  "reg_no": "Registration No",
  "phone": "Office Phone",
  "state": "State"
}
```

```powershell
py -3 resolve_entities.py load-entities `
  --db data/yp.duckdb --input ssm_export.csv `
  --column-map-file data/column_map.json
```

## How the score works

Signals are additive and capped at 1.0, then penalties are applied:

| Signal | Max |
| --- | --- |
| Name (Jaro-Winkler on suffix-stripped name, plus exact-core bonus) | 0.55 |
| Phone (full normalised match, then any-overlap, then 7-digit suffix) | 0.25 |
| Website domain (generic hosts ignored) | 0.15 |
| Address similarity (Jaro-Winkler) | 0.12 |
| Postcode | 0.07 |
| Coordinates (100 m / 500 m / 2 km) | 0.06 |
| State | 0.04 |

Penalties: conflicting phones −0.10, conflicting states −0.15, conflicting
postcodes −0.05, very different addresses −0.05, >20 km apart −0.05, and a
name/phone/domain combination that is too weak −0.15.

Default decisions:

* `auto` — score ≥ 0.82
* `review` — 0.62 ≤ score < 0.82
* `reject` — below 0.62

These are **not** universal truth. Calibrate on a labelled sample of your own
data instead of guessing:

```csv
outlet_id,entity_id,label
o1,202301234567,1
o2,202001111111,1
o3,201901222222,0
```

```powershell
py -3 resolve_entities.py calibrate `
  --db data/yp.duckdb `
  --labels labels.csv `
  --out data/calibration.json
```

It prints precision, recall and F1 at every threshold from 0.30 to 0.98, then
suggests an `auto` threshold that meets `--target-precision` (default 95%) and a
`review` threshold that meets `--target-recall` (default 90%). The suggestion is
the midpoint of the best-performing plateau, not the first row that happens to
pass. Below 50 labels it warns you that the numbers are indicative.

Then apply the suggested values:

```powershell
py -3 resolve_entities.py resolve `
  --db data/yp.duckdb --auto 0.88 --review 0.70
```

Raw outlet ids (`o1`) and registration numbers (`202301234567`) are accepted;
the tool adds the internal `ov:` / `ssm:` prefixes automatically.

## Matching safeguards

* **Blocking, not a cross join**: candidates come from exact name core, phone
  suffix, domain, name-prefix + postcode, and name-prefix + state.
* **Candidate cap**: aborts above 20M pairs (`--max-candidates`) instead of
  silently running for hours.
* **`--active-only`**: restricts entities to active SSM records. Recommended for
  lead generation; omit it for historical research.
* **`--canonical-only`**: after outlet dedupe, resolve each physical shop once.
* **Top-N per outlet**: `--top` keeps alternatives for review instead of
  discarding them.
* **Evidence**: `links.evidence` records the names, JW score, phone/domain/
  postcode/state equalities and distance, so a reviewer can see *why*.

## Self-test

```powershell
py -3 resolve_entities.py self-test
```

It builds an in-memory database with five outlets (including one duplicate) and
three entities, then asserts: exact name + phone + postcode goes to `auto`;
name + address + postcode goes to `review`; conflicting phone and state are
`reject`; an unknown shop stays unmatched; the duplicate pair is clustered.

## Important limits

* This tool does **not** include SSM data. You must supply a licensed SSM
  e-CBID/MyDATA export, or your own records. Do not scrape SSM against its terms.
* Matching is deterministic and heuristic, not a trained model. The review queue
  is part of the design, not an optional extra.
* One legal entity can own many outlets; that is expected and reported as
  "Entities w/ >1 outlet".
* Overture categories and SSM MSIC codes are different taxonomies. The resolver
  links identity, not industry; map MSIC separately if you need sector filters.
* Names are normalised but not transliterated. Chinese, Malay and English names
  are preserved; cross-script matching will usually land in `review`.

duplicate and three multi-branch brands, an optional SSM export, and labelled
pairs for calibration. See `examples/README.md` for the exact commands and

# Address validation

`build_osm_reference.py` builds the reference, `pilot_validate.py` measures it,
and `validate_address.py` is the usable internal validator.

## The validator

It accepts a batch file or a single address, and does not require coordinates.
Candidates are anchored on a per-street OSM address centroid when one exists,
then the postcode centroid, then the locality or state centroid.

```powershell
# One address -> JSON
py -3 validate_address.py --address "12, Jalan Ampang" `
  --postcode 50450 --city "Kuala Lumpur" --state "Kuala Lumpur"

# Batch: CSV, JSONL, JSON or Parquet in; CSV or JSONL out
py -3 validate_address.py --input addresses.csv --out validated.csv
```

Python:

```python
from validate_address import AddressValidator

validator = AddressValidator()          # load once, keep it warm
result = validator.validate(
    address="12, Jalan Ampang", postcode="50450", state="Kuala Lumpur"
)
```

Verdicts: `valid`, `valid_street_number_unverified`, `probable`, `corrected`,
`unverified`, `unverified_area`, `unverified_no_street`, `invalid_postcode`,
`invalid_state`, `invalid_input`. `street_source` says whether the street was
confirmed by an OSM address point (`osm_address`), a road segment (`osm_road`),
or neither (`none`).

On the same 1,000-address sample used by the pilot, but with **no coordinates**
(postcode/locality only), the validator returns:

| Verdict (street rows, n=802) | Count | Share |
| --- | --- | --- |
| `valid` | 220 | 27.4% |
| `valid_street_number_unverified` | 284 | 35.4% |
| `probable` | 29 | 3.6% |
| `corrected` | 8 | 1.0% |
| `unverified` | 261 | 32.5% |

Across all 1,000 rows: postcode is official for 99.5%, state agrees for 100% of
rows with an official state, and a house number is confirmed for only 19 of 524
parsed numbers (3.6%). Street evidence comes from an OSM road for 731 rows, an
OSM address point for 213, and neither for 56.

The conservative behaviour is intentional:

* **Numeric suffix changes are not corrected.** `Jalan Batu Nilam 34` is not
  "corrected" to `Jalan Batu Nilam 4`.
* **Only genuine typos are corrected** (`Ferringgi` -> `Ferringhi`,
  `Yusuff` -> `Yusuf`).
* **Absence is not invalidity.** Missing OSM coverage returns `unverified`, not
  `invalid`.

## Build the reference

```powershell
# Official postcodes: MCMC via data.gov.my, CC BY 4.0
Invoke-WebRequest -Uri 'https://storage.data.gov.my/dictionaries/postcodes.parquet' `
  -OutFile data/postcodes.parquet

# Malaysia + Singapore + Brunei OSM extract, ODbL, ~240 MB
Invoke-WebRequest `
  -Uri 'https://download.geofabrik.de/asia/malaysia-singapore-brunei-latest.osm.pbf' `
  -OutFile data/osm/my-sg-bn.osm.pbf

# Named roads with line geometry + address points, filtered to Malaysia
py -3 build_osm_reference.py `
  --pbf data/osm/my-sg-bn.osm.pbf `
  --out-dir data/osm `
  --regions data/my_regions.parquet

# Score 1,000 Overture addresses
py -3 pilot_validate.py --sample 1000
```

`data/my_regions.parquet` must contain a `geom` column of state polygons. The
current file holds the 16 Malaysian `region` polygons from Overture's divisions
theme (`country = 'MY'`, `is_land = TRUE`).

Outputs: `data/osm/roads.parquet` (331,729 named roads), `data/osm/addresses.parquet`
(239,688 address-tagged objects), `data/pilot_results.csv`.

## Precision review

Coverage is not precision. `make_review_sheet.py` builds a blind 250-row sheet
from the validator output; it hides the verdict, confidence, similarity and
evidence source so the reviewer only answers: is the matched road the street in
the address?

```powershell
py -3 make_review_sheet.py            # 250 rows
# or: py -3 make_review_sheet.py --scale 0.4   (about 100 rows)
# label data/review_sheet.csv (1 = correct, 0 = wrong, blank = skip)
py -3 score_review.py
```

For a real geographic audit, build the map-linked sheet instead:

```powershell
py -3 make_geo_review_sheet.py      # 100 rows, all uncertain rows + risky tiers
```

`data/review_sheet_geo.csv` includes the input coordinates plus Google Maps links
for the address, the pin and the matched road. Do **not** auto-label by comparing
strings: that reproduces the validator's rule and reports artificially high
precision. The question is whether the matched road is at the address's location.
See `REVIEW_INSTRUCTIONS.md`.

The scorer reports precision overall and by verdict, street source, state group
and distance, with 95% Wilson intervals, and writes `data/review_scores.json`.
See `REVIEW_INSTRUCTIONS.md` for the labelling rules. Targets: `valid` and
`valid_street_number_unverified` >= 95%, `probable` >= 80%, overall claimed
>= 90%.

## What the pilot found

On a deterministic 1,000-address sample from the 2026-10-21.0 Overture pull:

| Check | Result |
| --- | --- |
| Postcode in official MCMC table | 99.5% |
| Derived state agrees with MCMC postcode state | 100% (995/995) |
| Street address parsed | 99.9% of street rows |
| Strong street match (Jaro-Winkler >= 0.95) | 84.2% of street rows |
| Within a loose correction (>= 0.78) | 98.8% of street rows |
| Median distance to matched road | 21 m |
| House number found in OSM | 7.2% of parsed numbers |

The important caveats:

* **Postcode and state are strong; city is not.** Only 69% of `locality` values
  matched MCMC's `city` (neighbourhood vs town), so treat city as advisory.
* **Street matching is good in urban areas and weaker in rural ones.** Strong
  matches: Kuala Lumpur 95.6%, Pulau Pinang 94.9%, Johor 92.6%, Selangor 90.1%.
  Sabah 65.6%, Kelantan 66.7%, Terengganu 53.3%.
* **Fuzzy correction is unsafe.** In the 0.78-0.92 band, 45 of 100 matches were
  more than 200 m away and were different streets (`Jalan Besar` -> `Jalan Pasar`).
  Do not auto-correct from similarity alone; return a suggestion with low
  confidence instead.
* **House-number validation is not viable at scale** with OSM (7.2%). Return
  "street valid, number unverified" rather than "invalid".
* **Area-only addresses need a different path.** "Kampung X" or "Bandar Y" should
  validate postcode/locality/state, not a street.

Recommended verdict tiers: `valid`, `valid_street_number_unverified`,
`probable`, `corrected`, `unverified`, `unverified_area`,
`unverified_no_street`, `invalid_postcode`, `invalid_state`, `invalid_input`.
Never return "invalid" merely because a reference is absent.
